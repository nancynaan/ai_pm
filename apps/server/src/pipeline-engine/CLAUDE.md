# Pipeline engine

Loaded when working in `apps/server/src/pipeline-engine`. The product's pipeline: deterministic TypeScript that runs the stages; agents only give judgements.

## Map

- `stages.ts`: run states and allowed transitions (the state machine). `engine.ts`: `createPipelineEngine` runs each active state as a pg-boss job under a per-run advisory lock (a job that finds the lock held is re-queued after 2 s, never dropped: the action that enqueued it may still hold the lock), records attempts in `stage_executions`, retries failures (3 attempts with backoff), pauses on the Claude usage limit, and handles client actions (answers, discovery decision, decision, retry). `queue.ts`, `events.ts`, `repository.ts`: jobs, SSE events, database access.
- `stages/`: one handler per stage (`intake`, `eliciting` = discovery, `analyzing`, `estimating`, `documenting`, `presenting`, `backlog`). `placeholder.ts` is only the walking skeleton for the engine tests; the server registers no placeholder. `prompts.ts`: shared prompt helpers.
- `backlog/`: stage 06. `plan.ts` (pure: the backlog-builder prompt, `coverageGaps`, `checkBacklogDraft` = the DoR gate, `proposePriority`, `buildBacklogPlan` = the Jira issues with descriptions, labels and estimates), `write.ts` (the Jira writes through the publisher and the Initial Product Backlog block), `repository.ts` (`backlog_sets` draft cache, `backlog_items` with the Jira keys). `stages/backlog.ts` runs it; `prepareBacklog` is shared with the dry-run CLI (`evals/backlog-cli.ts`).
- `documents/`: stage 04. `inputs.ts` (what the documents are built from), `figures.ts` (the figure registry: every printed value by key), `tables.ts` (every table, from the DB), `templates.ts` (loads `skills/pm-artifacts/templates`), `render.ts` (Markdown preview + Confluence storage), `validate.ts` (draft and result checks), `prompt.ts` (the pm-writer prompt), `publish.ts` (the Confluence page tree and the shared-page blocks), `repository.ts` (FA numbers, cached draft, document rows).
- `presentation/`: stage 05. `deck.ts` (`deckFacts`: every number on the three slides; `buildDeck`; the presenter prompt), `validate.ts` (deck wording checks), `repository.ts` (deck, version, attachment). The PPTX renderer is `src/render/pptx.ts`.
- `discovery.ts` + `discovery-config.ts`: the fixed questionnaire (`config/discovery.yaml`), submission checks, completeness rules and the Discovery Completeness Report.
- `assessment.ts` + `assessment-config.ts` + `calculators/`: the Phase 4 assessment (`config/feasibility-rules.yaml`).
- `services.ts` (what stages may use), `context.ts` (baseline and Jira context), `analysis-repository.ts` (analysis and assessment persistence), `magnitude.ts` (change-magnitude rule).

## Rules

- **A stage handler** gets a `StageContext`, may call agents only through `services.ask` and data only through `services`/`ctx.repo`, emits events with `ctx.emit`, and returns `{ next, output }`. `next` must be an allowed transition in `stages.ts`; add new states there first. Register the handler in `apps/server/src/pipeline.ts` (`createPipeline` wires every stage; `index.ts` and the end-to-end test both use it).
- **No arithmetic in prompts.** Every number comes from `calculators/` (pure functions). Agents give story points, ratings and KPI effects; code turns them into dates, money and verdicts. Keep calculators free of I/O and seed every random draw (`seededRng(seedFrom(runId))`).
- **Discovery:** rules in code decide coverage, contradictions, gaps, evidence and readiness; the discovery-review agent only adds what rules cannot see. Information is labelled confirmed, client assumption, AI hypothesis or missing; missing or unproven information never becomes a fact. Confidence is "low" only for blocking issues, critical gaps or 4+ questions the client left open.
- **Assessment:** the forecast never runs faster than the busiest discipline (a "bottleneck" is planning information, not a condition); contingency = Σ risk EMV capped at 30 % of labour P50; a plain Go has no conditions (the team re-estimate is a standard next step); an incomplete discovery makes every verdict preliminary.
- **Documents:** the run waits in `awaiting_documents` until the client presses "Generate documents" (`generateDocuments`) or "Skip for now" (`skipDocuments`, any verdict, straight to `presenting`). The documents stage only generates: rows are saved as `generated` (previews) and the run goes on to `presenting`, or back to `awaiting_decision` when the client generates them late at the decision (`lastSucceededAt(presenting)`; request key `documents.request.late`). Generated once: no re-generation. Publishing is a separate client action (`publishDocuments` → `publishing.ts` → `publishStoredDocuments`), once, at any time after generating; there is no re-publish. **Approve needs the documents published** (`documentsStatus` in the engine options): otherwise `decide` refuses with 409 and posts what is missing (`decision.blocked`). Later steps (deck publish, decision, backlog) update pages only if they were published (`republishDocuments`), under the per-run publish lock (`publishing.locked`) that serialises every page write. One pm-writer call writes the text of all documents and is cached by its inputs, so an unchanged assessment never calls Claude again. The writer cites computed values only as `{{figure:key}}`; `checkDraft` rejects other numbers unless the client or the requirements state them. Pages are found by the sync log, then by title, and rewritten in place (`overwrite`); shared pages get one anchored block per feature (`spliceBlock`). Agent text is defused (`{{` → `{ {`) before it enters a template.
- **Presentation:** three slides only (business opportunity, solution & scope, delivery feasibility & recommendation). The presenter words headings and labels; `deckFacts` supplies every number. Never story points: delivery is a date range and budget a money range (P50–P85), both marked preliminary, and every slide says the estimate is not a commitment. A retention effect without strong evidence is a hypothesis. The stage never uploads the deck: the client publishes it once from the Proposal card (`publishPresentation`), only after the documents are published; it is attached to the Feature Brief (one file, `proposalFileName`) and the Brief is re-rendered to embed it with a `view-file` macro (`links.deck`, from the attachment sync key); until then the Brief says the presentation is not published. In the chat the question (`decision.prompt`) comes before the decision card.
- **Decision:** Approve or Decline only (no "request changes"). On a decline, `onDecision` (`documents/recordDecision`) re-renders the documents from the stored draft so the Brief and the Assumption Log show it (only if they were published), closes the draft Epic and closes the conversation. An approval is recorded by the backlog stage instead (`republishDocuments`), because two writers on the same pages would race.
- **Backlog (stage 06):** the coverage gate (every requirement except Won't has a story-map item) runs before any Claude call; one backlog-builder call writes the Epic text and one story per story-map item (cached in `backlog_sets` by its inputs without the live Jira backlog, so our own new issues never invalidate it); `checkBacklogDraft` is the DoR gate in the repair loop. Code sets priority (MoSCoW, +1 for a starting point: an item others wait for that waits for nothing), the AI estimate (PERT mean, one decimal) and labels (`ai-pm`, `ai-draft`, `fa-<n>`, kind, marker). Jira gets the Epic (created, or the intake draft completed) and Stories under it, To Do, no sprint, Story Points never set; `Blocks` links are read before they are written (a reversed link is replaced once and the direction remembered). Then the Initial Product Backlog block (`aipm-fa-<n>`), the documents re-render (Epic key in the Brief title, Epic and backlog links) and one card plus a closing message; the run ends in `completed` (shown as Approved).
- **One block per step in the chat:** a step's card or message is emitted with a key (`ctx.emit(event, 'presentation')`, `bus.publish(runId, event, key)`); emitting it again rewrites the stored event in place (same id and position) and the chat updates it. Keys in use: `assessment`, `documents.request`, `documents.status`, `documents.result`, `presentation`, `decision`, `decision.prompt`, `decision.response`, `decision.recorded`, `decision.blocked`, `documents.request.late`, `documents.published`, `presentation.status`, `presentation.published`, `backlog.result`, `backlog.closing`. Re-runs must never add a second card for the same step.
- Settings and thresholds belong in `config/*.yaml` (validated by a strict zod schema at startup), not in code.

## Tests

Stage tests use fake repositories and services (see `stages/stages.test.ts`, `stages/estimating.test.ts`); the engine test uses in-memory stand-ins for Postgres, the lock and pg-boss (`engine.test.ts`). Calculators are tested with fixed seeds and hand-checked numbers (`calculators/calculators.test.ts`). Shared fixtures (a small feature with fake agent answers) live in `testing/fixtures.ts`, which the build excludes. `documents/documents.test.ts` publishes against a fake Confluence (dry-run, first publish, re-publish, edited page). `backlog/backlog.test.ts` covers the gates, priorities, Gherkin, a fake Jira (dry-run, first write, idempotent re-run, completing the intake Epic, a reversed link, the Initial Product Backlog block) and the stage. The end-to-end test (`src/e2e/pipeline.e2e.test.ts`, runs when `E2E_DATABASE_URL` is set, as in CI) drives `createPipeline` with a real Postgres, the client from `evals/features.yaml`, Claude answers replayed from `evals/cassettes/rewarded-menu-chest.json` (`agents/cassette.ts`: per agent, in call order) and a fake read-only Atlassian site (`e2e/fake-atlassian.ts`): one run approved, one declined. A change that adds or reorders agent calls needs a re-recording (`E2E_RECORD=1`, through the app container). A change to prompts, skills or rules is checked with the eval (`/eval`), not only unit tests.
